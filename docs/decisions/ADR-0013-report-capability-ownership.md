# ADR-0013：报告能力职责归属——联动 vs 分离

- 状态：Accepted（R1–R5 已实现并由自动化测试覆盖；R6 真机验证仍按[主计划 9.2](../llrp-framework-vision.md)与 planning 文档归档）
- 日期：2026-08

## 决策

联动范围只限“**需要上报控制**”的参数，按“是否只影响 TagReport 展示字段”分两类归属：

- **联动式（A）**：开关只决定“报告里多不多一个字段”（例如 Phase/GPS/XPC），由寻卡页列开关触发，服务层按当前激活扩展自动分发（标准 LLRP / Impinj / Zebra）。
- **分离式（B）**：开关直接影响读标签行为（不只是展示），例如 FastID/Serialized TID，保持在设置页独占控制；寻卡页只负责展示这些字段的列，不提供开启入口。

**只读原则**：一项参数一旦决定联动、或已实现真实联动，设置页对同名项即改为**只读**并提示“由寻卡页联动控制”，不再提供第二个可写入口；未决定联动前保持现状可写。

以语义键为统一收口：UI（寻卡页、设置页）只认稳定语义键，不直接碰厂商 Key；服务层按当前激活扩展把语义键编译到对应厂商参数。

## 背景

- 报告字段（RSSI/天线/信道/PC/时间/SeenCount/Phase 等）经 `InventorySpec.Report` 在寻卡启动时覆盖到 LLRP；扩展报告字段由寻卡页列开关产生语义请求，服务层再按激活扩展编译到厂商参数。
- 若同时在寻卡页和设置页提供同一能力开关，会出现两个入口、两套联动逻辑，难以保证一致性。
- 标准 LLRP 1.0.1 没有 RF phase 报告字段；相位必须是厂商扩展（Impinj RF Phase / Zebra report phase）或未来标准版本吸收后的语义路径。

## 候选方案

1. **两端都控制（现状）**：寻卡页 + 设置页各自可开关同一能力。导致双入口、双联动、状态容易不一致。
2. **寻卡联动 + 设置隐藏**：报告类只由寻卡页列开关控制，服务层按厂商 dispatch；设置页该项隐藏或只读提示。一致性最好。
3. **寻卡只显示 + 设置独占（分离）**：寻卡页不写设备，只在设置页开。对数据能力（FastID）正确，但纯报告字段会让寻卡页操作冗长。

## 原因

- 纯报告字段天然与“我这一列要不要显示”一致，由寻卡页控制最直观，且满足“寻口界面列开关自动下发 LLRP 参数”的期望。
- 数据能力（如 FastID）影响标签可读性本身，只应在设置页做，避免寻卡页误改设备行为。
- 语义键收口让 WPF 不碰 SDK，符合依赖方向与“UI 不直接编译厂商参数”的约束。

## 影响

- 报告类字段（Phase 等）将来由寻卡页列开关触发；标准字段已经在 `TryBuildStartSpec` 映射到 `InventoryReportSpec`。
- `InventoryReportSpec` 需扩展支持扩展字段（按语义键），服务层（ReaderManager）按激活扩展编译到 Impinj/Zebra。
- **逐项生效**：某项实现真实联动后，设置页对应报告项才由可写改为只读 + “由寻卡页联动控制”提示；尚未联动的项保持现状，不做一次性批量只读。
- 数据能力（FastID 等）保持设置页控制，寻卡页仅展示。
- 当前实现：`ReportFieldSemantics` 位于 Contracts；Impinj/Zebra 扩展分别实现
  `ApplyInventoryReportSpec` 和 `ProjectTagReport`，将 Phase/GPS/XPC 投影为稳定语义字段；
  WPF `TagRowViewModel` 只读取这些语义字段。设置页的同名报告开关由扩展贡献者标记为只读，
  并保留“由寻卡页联动控制”提示。厂商原始字段仍可作为诊断扩展字段保留，但不属于 UI 契约。
