04 / CORE ARCHITECTURE & PLATFORM SERVICES

Platform services and application boundaries

LlrpReaderPlatform is an application service platform built on LLRPCSharp, not a second LLRP SDK. It coordinates reader lifecycle, session leases, settings projection, local persistence and multiple UI composition roots.

Layering and dependency direction

The repository keeps business services testable and dependencies flowing toward contracts and the SDK:

App.Wpf / LlrpReaderManager (composition roots)
  ├──► Services ───────────────► Contracts + LlrpSdk
  ├──► Infrastructure ─────────► Services + Contracts
  └──► Extensions.* ───────────► Services + Contracts + vendor SDK adapter

Contracts (DTOs / interfaces / error codes; no UI or SDK dependency)
Services (reader lifecycle / leases / settings / inventory / Tag Access)

LlrpVirtualDevice.App.Wpf
  └──► LlrpDevice.Virtual.Hosting (independent TCP virtual-reader tool)
Architecture tests: Contracts must not depend on WPF, generated SDK messages or vendor-specific types.

ReaderHandle ownership and leases

Most readers expose one meaningful TCP/session state machine. ReaderHandle makes ownership explicit:

SHORT LEASE

Short operation

Probe, settings application, Tag Access and supported GPIO operations take a short lease and release it after completion.

LONG LEASE

Inventory ownership

Inventory owns the session from start to stop and receives the report stream through that channel.

DETERMINISTIC

Busy is explicit

Lease contention returns ReaderBusy rather than issuing conflicting commands or silently restarting a reader.

EF Core SQLite persistence

LlrpReaderPlatform.Infrastructure uses EF Core and SQLite for local structured data.

ReaderProfileEntity       : reader address, name and capability cache
SettingsPresetEntity      : antenna / RF-mode / power presets
TargetOfInterestEntity    : EPC, category and highlight metadata
InventoryRunEntity        : run history and explicit stop reason
AppSettingsEntity         : local UI and application preferences

Vendor extension modules

After a reader is connected, the platform can project vendor data using the enterprise number and registered adapter.

  • Impinj (IANA 25882): primary extension path for Search Mode, Low Duty Cycle, Serialized TID and RF phase semantics.
  • Zebra (IANA 161): experimental module; advanced fields and settings require model/firmware validation.
  • Standard readers: use the common LLRP path when no vendor extension is matched.

Platform error codes

  • ReaderNotFound: the reader handle is missing or removed.
  • ReaderBusy: an exclusive lease is already held.
  • ConnectionFailed: TCP connection or network setup failed.
  • ProtocolError: an unexpected LLRP error response was returned.
  • CapabilityMismatch: requested settings exceed the device capability model.

Physical hardware acceptance baseline

Compatibility claims are based on recorded true-device evidence, not only mocks or unit tests.

  • Impinj Speedway Revolution R420 (LLRP 1.0.1): primary true-device baseline with connection, capabilities, settings, inventory and some Tag Access/vendor-field evidence; remaining items are tracked in the acceptance table.
  • Standard LLRP 1.0.1: connection, capability and some settings evidence exists; inventory and Tag Access depend on the target device and site conditions.
  • Standard LLRP 1.1 / 2.0: software and automation coverage exists; true-device interoperability remains pending.
  • Zebra FX9600: experimental extension; identity/connection evidence exists, while advanced behavior remains to be calibrated.
